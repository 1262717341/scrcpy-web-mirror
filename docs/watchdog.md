# 手机端看门狗（v4.0.12 重新梳理）

## 一句话职责

> **无线会话失联 → 结束手机端 scrcpy、释放音频采集 → 自己退出。**

只做这一件事。不重连、不诊断网络、不改用户的勿扰/音量/亮度设置。

## 为什么必须由手机自己动手

手机主动关 Wi-Fi 或走出路由器范围时，电脑根本连不上手机，任何"从电脑远程清理"的方案都会失败。
而断网后内核会把 scrcpy 的 socket 挂住十几分钟，进程不会自己退出，音频采集一直被占着
—— 这就是"断完网手机长时间没声音"的根因。清理动作必须已经在手机本地跑着。

## 判据只有两条

| 判据 | 阈值 | 说明 |
| --- | --- | --- |
| 会话心跳过期 | 5s | 页面每 2s 通过现有 ADB 通道写一次心跳（`<时间戳> <会话号>`）。**写进去本身就证明通道还活着**。心跳周期远小于判定阈值，留 3 秒抖动余量。后台标签页的定时器会被压到 1 分钟一次，所以心跳放在 Worker 里发。 |
| Wi-Fi 地址消失 | 连续 2 次（约 2s） | `ip -4 addr show wlanX` 读不到 `inet`。关 Wi-Fi / 掉线是确定事实，不必等心跳过期。检查循环 1s/次。 |
| 从没见过心跳 | 20s | 布防前一定先写一次心跳；读不到说明写失败或文件被清，按失联处理。 |

已删除的旧判据：ping 网关、数 `/proc/net/tcp` 里 5555 的 ESTABLISHED 条目、端口猜测。
它们慢（每次要多跑几条 shell）、且会误判（换网、双 Wi-Fi、VPN 都会让结论失真）。

## 生命周期

```
prepareDevice()      一次 shell：清掉上一轮 guard / scrcpy 残留 + 读回 SDK
        │
        ├── deployAudioGuard()  ┐ 并行
        │     写脚本 → sh -n 校验 → 置一次心跳 → nohup 起进程 → 轮询回读运行标记
        │                       ┘
        └── AdbScrcpyClient.start() → 首帧
```

- **会话号隔离**：每轮无线会话生成一个短号，心跳与运行标记都带会话后缀
  （`/data/local/tmp/panda_hb.<会话号>`）。另一个窗口、上一轮会话都写不到本轮的文件。
- **新会话接手即退场**：guard 每轮都看心跳里的会话号，发现换成别人就静默退出，绝不动新会话的 scrcpy。
- **主动停止**：`releaseSessionOnDevice()` 一次 shell 完成「guard 退场 → TERM/KILL scrcpy → 净音量不变的音频路由刷新 → 回读剩余进程」，不再有 2 次 sleep 和 3 个往返。

## 失联时的动作

1. `pkill -TERM` scrcpy → 等 1s → `pkill -9`（含 `app_process` 兜底）
2. 音频路由刷新：读当前媒体音量 → 抬一格 → 原样写回（净音量不变、无 UI、不改勿扰）
3. 写一行日志（原因 + 剩余进程数）→ 退出

日志在 `/data/local/tmp/panda_guard.log`，只记关键事件（启动、被替换、失联、释放），不刷屏。

## 状态文件

| 文件 | 用途 |
| --- | --- |
| `/data/local/tmp/panda_guard.sh` | 脚本正文 |
| `/data/local/tmp/panda_guard.log` | 关键事件日志 |
| `/data/local/tmp/panda_hb.<会话号>` | 心跳：时间戳 + 会话号 |
| `/data/local/tmp/panda_run.<会话号>` | 运行标记：guard 第一轮立即写，之后每 10s 一次 |

## 明确不做的事

- 不重连（重连是页面/服务端的事）
- 不改 `zen_mode`、不按音量键、不 set 固定音量
- 不判断"网络好不好"，只看"心跳在不在"
- 不做耗时诊断（诊断项放在「恢复声音」按钮里按需执行）
